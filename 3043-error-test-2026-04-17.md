# Workers AI 3043 Error — Empirical Probe

**Date:** 2026-04-17
**Target:** `https://hindsight-cf.enzinas.workers.dev` (prod)
**Model exercised:** `@cf/baai/bge-m3` (embeddings) — one call per probe via `/memories/recall` on an empty bank
**Probe script:** `tests/live-throttle-probe.ts`
**Per-call log:** `tests/probe-log.jsonl`

## Motivation

During a full live-test run we hit **3 HTTP 500s with body `"3043: Internal server error"`** across ~50 AI-touching calls. Workers AI error code `3043` is **not** in Cloudflare's official error table — we found it only via community posts where users report ~25% random failure rates on `@cf/baai/bge-m3` and vision-capable models, even at trivial request rates. Before building retry logic, we wanted empirical data: is 3043 load-driven, rate-driven, or just infrastructure flakiness?

## Background from Cloudflare docs & community

- **Official Workers AI errors table** lists 3040 (HTTP 429, "Out of capacity") as the rate-limit code. `3043` is absent.
- **Default text-gen rate limit:** 300 req/min. Embeddings: 3000 req/min.
- **Community reports (May–June 2025, still unresolved):**
  - `@cf/baai/bge-m3` — "1 in 4 invocations fail with 3043 with identical payloads"
  - `mistral-small-3.1-24b-instruct` + `llama-3.2-11b-vision-instruct` — vision inputs fail with 3043
  - AI Gateway `retries: { maxAttempts: 5 }` does **not** catch 3043
  - Both forum threads auto-closed after 15 days with no Cloudflare response.

## Methodology

Three phases, all well under the 3000 req/min limit for bge-m3:

| Phase | Rate | Duration | Calls | Retry policy |
|---|---|---|---|---|
| A | 1 call / 4 s | 200 s | 50 | None |
| B | 1 call / 1 s | 200 s | 200 | None |
| C | 3 calls / 1 s | 200 s | 600 | Immediate retry on 3043 until success |

Each call uses a unique query string (`probe-<phase>-<i>-<ts>`) to defeat any caching. Every response is recorded to `tests/probe-log.jsonl` with status, latency, and error snippet.

## Results

### Run 1 (afternoon)

| Phase | Calls | Successes | 3043 failures | 3040 (rate) | Latency p50 / p95 |
|---|---|---|---|---|---|
| A: 1/4s | 50 | 39 (78.0%) | **11 (22.0%)** | 0 | 270 / 495 ms |
| B: 1/1s | 200 | 195 (97.5%) | **5 (2.5%)** | 0 | 279 / 629 ms |
| **Combined** | **250** | **234 (93.6%)** | **16 (6.4%)** | **0** | **278 / 591 ms** |

Phase C was not included in Run 1.

**Failure clustering observed:**
- Phase A: 0 failures in first 20 calls (80 s), then 11 failures in next 30 (120 s) — back-loaded.
- Phase B: 5 failures in first 100 calls, then 0 failures in final 100 — front-loaded (looks like cold-start warmup).

### Run 2 (30 min later, same prod target)

| Phase | Calls | Successes | 3043 failures | 3040 (rate) | Latency p50 / p95 |
|---|---|---|---|---|---|
| A: 1/4s | 50 | **50 (100.0%)** | 0 | 0 | 149 / 276 ms |
| B: 1/1s | 200 | **200 (100.0%)** | 0 | 0 | 151 / 250 ms |

| **Combined** | **850** | **850 (100.0%)** | **0** | **0** | **114 / 213 ms** |

Phase C retry stats: **0 calls retried, 0 total retry attempts, max retries needed = 0.** Distribution `0:600` (all 600 calls succeeded first try).

| Metric | Run 1 | Run 2 |
|---|---|---|
| Phase A failure rate | 22.0% | 0% |

## Findings

1. **3043 is NOT rate-triggered.** Zero 3040 (the real rate-limit code) across **1,100 calls total**. Even at 3 req/s sustained for 200 s, nothing came close to the limit.
2. **3043 is NOT load-correlated within our test range.** The fastest cadence (Phase C, 3 req/s) had the lowest failure rate (0%) and the lowest latency (p50 106 ms).
3. **3043 IS incident-driven, not baseline-persistent.** Run 1 caught what looks like a transient CF backend incident (failures clustered in a 120 s window during Phase A); Run 2 — same worker, same probe, 30 min later — saw zero failures.
4. **Latency also drops when the backend is healthy** — p50 fell ~46% between runs, confirming both runs hit meaningfully different backend conditions.
5. **Community's "1 in 4" figure is an incident-window observation, not a steady-state rate.** Steady-state appears to be **<1%**, possibly near-zero.
6. **Retries during a healthy window are unneeded** — 0/600 retry calls in Phase C. Retries earn their keep only during the incident windows, where they are extremely valuable (e.g., single-retry clears ~94% of Run 1's failures; two retries would have cleared ~99.6%).

## Implications for hindsight-cf

- End users will intermittently hit 3043 during CF backend incidents, regardless of their request rate. The app needs transparent retry to mask this.
- A **two-tier retry strategy** is appropriate:
  - **Production:** wrap `env.AI.run(...)` in `src/providers/` with 2 retries at ~500 ms + 1500 ms backoff on 3043 / HTTP 5xx matching the pattern. Protects real users.
  - **Tests:** `apiCall` helper retries on the same signature with a clear `[HINT]` message so a new installer sees `"transient CF upstream error — retried N times"` instead of an unexplained 500.
- **No inter-block pacing needed** in tests — failure rate is uncorrelated with our throughput.
- **Separate treatment for 3040 / 429** if we ever see one: longer backoff (30–60 s), clearer "you are being rate-limited" hint. Not observed yet.
